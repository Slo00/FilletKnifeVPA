# ADR-002: перцентили считаются в MetricsQL, а не во внутренней гистограмме VPA

## Статус

Принято, 2026-09-14. Уточняет [0001-vm-metrics-source](0001-vm-metrics-source.md).

## Контекст

ADR-0001 зафиксировал, что источником метрик становится VictoriaMetrics,
опрашиваемая на каждом цикле, и что чекпоинты с прогревом отпадают.
Остался открытым вопрос *как* recommender превращает сырые замеры
в рекомендацию — архитектурная развилка:

- **Вариант A.** Оставить гистограммную модель VPA (`pkg/recommender/model`)
  с затуханием, подавать в неё сэмплы из VM через `MetricsClient`.
  Совместимо со штатным кодом, но модель дублирует то, что TSDB умеет
  одним запросом, и по сути противоречит духу ADR-0001 — состояние
  внутри recommender снова появляется.
- **Вариант B.** Перцентили и максимумы считает сама VictoriaMetrics
  через MetricsQL (`quantile_over_time`, `max_over_time`) по окну.
  Recommender не хранит историю между циклами вообще.

## Решение

Выбираем **Вариант B**.

- На каждом цикле recommender выполняет MetricsQL-запрос к VM и получает
  готовый агрегат, а не сырые сэмплы для внутренней гистограммы.
- Собственная модель с затуханием (`pkg/recommender/model`) для боевого
  пути не используется. `input/metrics.MetricsClient` (поллинг Metrics API)
  и `input/history.HistoryProvider` (прогрев при старте) в текущем виде
  не нужны — их функцию берёт на себя прямой запрос.
- Источник метрик — только VictoriaMetrics, без абстракции переключаемого
  источника (Prometheus отдельно поддерживать не требуется).
- Асимметрия CPU/RAM (CPU сжимаем — нехватка даёт троттлинг; память
  несжимаема — превышение лимита убивает процесс) реализуется разными запросами и окнами на тип ресурса, а не разными
  весами затухания в одной модели:
  - CPU — `quantile_over_time(0.9, ...)`, окно порядка дней/недели, запас.
  - Memory — `max_over_time(...)`, окно длиннее, снижение рекомендации
    медленное (логика вне самого запроса).

## Последствия

Плюсы:

- Закрывает главный практический отказ: нет прогрева — нет разрыва,
  когда recommender видит мало данных после рестарта или после вывода
  кластера на обслуживание и занижает рекомендацию до минимума.
- Recommender проще эксплуатационно: нет CRD-чекпоинтов, нет проблемы
  согласования состояния между репликами. Даёт измеримый показатель
  для экспериментальной главы — время восстановления после рестарта
  компонента, ожидается нулевым или близким к нулю.

Минусы / что остаётся спроектировать отдельно (не блокирует ADR):

- Пропадает встроенное в гистограмму затухание по времени. Нужно
  проработать через параметры запроса (длина окна, возможно `step`
  для скользящего окна), отдельный технический вопрос.
- Recommender зависит от доступности и времени ответа VM на каждом
  цикле, а не только при старте (это уже отмечено в ADR-0001 —
  требование «при недоступности хранилища сохранять прежние значения»
  теперь применимо к каждому циклу, а не только к старту).
- Нужно проверить, не используется ли `VerticalPodAutoscalerCheckpoint`
  чем-то ещё в updater/admission-controller (их не трогаем) прежде чем
  переставать его писать.
- Профили нагрузки «периодический» и «растущий»
  нужно валидировать именно на MetricsQL-запросах (окно под суточную
  сезонность, скорость реакции на рост) — часть будущих экспериментов,
  не ADR.

## Альтернативы

Вариант A отклонён: сохраняет состояние внутри recommender, что
противоречит ADR-0001, и дублирует агрегацию, которую TSDB уже умеет
делать запросом.
